## Summary

Phase 03.1 adds `ElevenLabsRealtimeClient` as a lean WebSocket transport adapter for ElevenLabs Agents (speech-to-speech) satisfying `RealtimeAdapterContract`. The implementation mirrors `OpenAIRealtimeClient` in structure with three key differences: (1) server-side VAD means `commit_client_turn()` and `create_response()` are no-ops; (2) audio sample rate is 16 kHz, not 24 kHz; (3) the `user_audio_chunk` message is sent as a top-level key (not nested under `type`), confirmed from the official Python SDK source.

All 4 open points from the design doc have been **resolved** via the official ElevenLabs Python SDK source code (`elevenlabs-python` v2.49.1, verified 2026-05-25) and the official `ElevenLabsEnvironment` enum. The `tool_result_submission_mode` open point is the most significant: ElevenLabs uses a **native** `client_tool_result` message (not the OpenAI `conversation.item.create` pattern), so the capability value `"conversation_item"` in the design is **misleading** — the planner must use `"elevenlabs_tool_result"` or keep `"conversation_item"` as a documentation-level label if the consuming bridge understands it differently. See Open Point 4 resolution below.

The `agent_response_complete` event in the design was **not found** in the current SDK source (v2.49.1 sync+async dispatch). It was added to the public API schema in April 2026 (changelog entry) but is described as a **client-observable event**, not a server-pushed WebSocket wire event — it may be an API-level concept, not a raw WebSocket frame. The planner must treat the `RESPONSE_DONE` mapping as driven by `agent_response` (current agent text) rather than `agent_response_complete`. See Open Point 3 for details.

**Primary recommendation:** Implement against the verified SDK wire protocol. No new optional dependencies are required — `websockets>=13.0` is already in the `[realtime]` extra.

## RESOLVED: The 4 Open Points

### Open Point 1: EU-Residency Endpoint — RESOLVED

**Status:** RESOLVED

**Finding:** ElevenLabs provides a dedicated EU environment with a different base URL, **not** an account-level setting only.

**Verified EU base URL (HTTP/REST):** `https://api.eu.residency.elevenlabs.io`
**Derived WSS base URL:** `wss://api.eu.residency.elevenlabs.io`
**ConvAI agent endpoint (EU):** `wss://api.eu.residency.elevenlabs.io/v1/convai/conversation?agent_id={agent_id}`

**Source:** `ElevenLabsEnvironment` enum in the official Python SDK:
```python
# github.com/elevenlabs/elevenlabs-python/src/elevenlabs/environment.py (verified 2026-05-25)
class ElevenLabsEnvironment(enum.Enum):
    PRODUCTION = "https://api.elevenlabs.io"
    PRODUCTION_US = "https://api.us.elevenlabs.io"
    PRODUCTION_EU = "https://api.eu.residency.elevenlabs.io"
    PRODUCTION_INDIA = "https://api.in.residency.elevenlabs.io"
```
[VERIFIED: github.com/elevenlabs/elevenlabs-python/src/elevenlabs/environment.py]

**Implication for implementation:**
- `ElevenLabsRealtimeConfig.base_url` default: `"wss://api.elevenlabs.io"` (global, as in the design)
- EU consumers override with: `base_url="wss://api.eu.residency.elevenlabs.io"`
- The endpoint path `/v1/convai/conversation` is the same for both environments; only the base changes.
- The SDK's `build_ws_url()` converts `https://` → `wss://` scheme automatically; our implementation must do the same conversion (i.e., strip the scheme from `base_url` if it starts with `https://`).
- **Note:** A separate LiveKit endpoint exists for RTC: `wss://livekit.rtc.eu.residency.elevenlabs.io` — this is for real-time communications (not the convai WebSocket). The adapter uses only the convai endpoint.

**Important:** EU residency requires an **Enterprise plan** and a **separate API key** provisioned for the EU environment. The EU API key is different from the global API key. This must be documented in the GDPR guide.

### Open Point 2: Signed-URL Flow vs. xi-api-key Header Auth — RESOLVED

**Status:** RESOLVED

**Finding:** ElevenLabs supports **two authentication modes** for the convai WebSocket:

| Mode | When used | Mechanism |
|------|-----------|-----------|
| **Direct (public agent)** | Agent `requires_auth=False` | Connect directly with `?agent_id=` in URL; no header required |
| **Signed URL (private agent)** | Agent `requires_auth=True` | Server calls REST API with `xi-api-key` header → gets signed WSS URL → client connects to that URL (no header on WS connection) |

**Source:** Official Python SDK `conversation.py` line 709:
```python
# github.com/elevenlabs/elevenlabs-python/src/elevenlabs/conversational_ai/conversation.py
ws_url = self._get_signed_url() if self.requires_auth else self._get_wss_url()
```
[VERIFIED: github.com/elevenlabs/elevenlabs-python/src/elevenlabs/conversational_ai/conversation.py]

**Signed URL details:**
- REST endpoint: `GET https://api.elevenlabs.io/v1/convai/conversation/get-signed-url?agent_id={agent_id}`
- Header: `xi-api-key: {api_key}` (on the REST call, NOT on the WebSocket connection)
- Expiry: **15 minutes**; existing connections are not closed on expiry, but new connections will fail

**Implication for Phase 03.1:**
The design specifies `"Auth via xi-api-key header (private agent) or the signed-URL flow"`. The SDK source clarifies:
- For **private agents**, the `xi-api-key` is used in the REST call to get a signed URL, NOT as a WebSocket header.
- The WebSocket itself connects to the signed URL with no additional auth headers.
- For **public agents**, no auth is needed on the WebSocket connection.

**Recommended implementation:** The adapter should support both modes via an optional `signed_url: str | None = None` field on `ElevenLabsRealtimeConfig`. If `signed_url` is provided, use it directly for the WebSocket connection (bypassing the REST call). If not, use the standard `wss://{base_url}/v1/convai/conversation?agent_id={agent_id}` URL. This avoids requiring the adapter to make REST calls before connect.

**GDPR implication:** The `xi-api-key` must be redacted from all logs. Since the key is used in the REST call (not the WS URL for private agents), `_safe_url()` only needs to redact the base URL; the key itself never appears in the WebSocket URL for private agents. For public agents, the key is not used in the URL at all. The key must still be redacted from any error messages that may include it.

### Open Point 3: Precise Event Names of Current convai WebSocket Protocol — RESOLVED

**Status:** RESOLVED (with one important correction)

**Source:** Official Python SDK `conversation.py` dispatch code (sync and async, verified 2026-05-25)
[VERIFIED: github.com/elevenlabs/elevenlabs-python/src/elevenlabs/conversational_ai/conversation.py]

#### Server-to-Client Events (verified exact names)

| Wire event type | Sub-event key | Design mapping | Verified? |
|-----------------|---------------|----------------|-----------|
| `conversation_initiation_metadata` | `conversation_initiation_metadata_event` | `SESSION_READY` | YES |
| `audio` | `audio_event` → `audio_base_64` | `RESPONSE_AUDIO_DELTA` | YES |
| `agent_response` | `agent_response_event` → `agent_response` | text only, no normalized event | YES (note below) |
| `agent_response_correction` | `agent_response_correction_event` | not in design; emit `UNHANDLED` | YES |
| `user_transcript` | `user_transcription_event` → `user_transcript` | `INPUT_AUDIO_COMMITTED` | YES |
| `interruption` | `interruption_event` → `event_id` | `INPUT_SPEECH_STARTED` or cancellation | YES (note below) |
| `ping` | `ping_event` → `event_id`, `ping_ms` | Respond `pong`, not emitted | YES |
| `client_tool_call` | `client_tool_call` → `tool_name`, `tool_call_id`, parameters | `TOOL_CALL_COMPLETED` | YES |

**Critical correction — `agent_response_complete`:**
The event name `agent_response_complete` from the design **is NOT in the current SDK source** (v2.49.1). The SDK changelog (April 27, 2026) added `agent_response_complete` as an **API-schema concept** (enum value `AGENT_RESPONSE_COMPLETE` in `ClientEvent`). However, the SDK's message dispatch code (the live wire protocol handler) only has `agent_response` and `agent_response_correction` — not `agent_response_complete`. This event may be a **client SDK callback concept**, not a raw WebSocket frame that the adapter will see.

**Recommendation:** Map `agent_response` → emit no normalized event (text-only; audio comes via `audio` events). Map `RESPONSE_DONE` to the end of the audio stream (when the `audio` events stop, or watch for a turn-end signal). Add `agent_response_complete` to the dispatch as a potential future event that routes to `RESPONSE_DONE` if it appears — it will gracefully fall through to `UNHANDLED` if not received.

**VAD / interruption clarification:**
The SDK only has a single `interruption` event (not separate `speech_started` / `speech_stopped`). The `interruption` event signals that the user interrupted the agent. There is NO `vad_score` event in the core SDK dispatch (it may be an optional monitoring feature). Map:
- `interruption` → `INPUT_SPEECH_STARTED` (user started speaking, agent interrupted)
- No server-sent `speech_stopped` analog found; omit `INPUT_SPEECH_STOPPED` mapping unless docs show otherwise

#### Client-to-Server Messages (verified exact names)

| Message type (key) | Format | Purpose |
|-------------------|--------|---------|
| `{"user_audio_chunk": "<base64>"}` | Top-level key, NOT a `type:` message | Audio input |
| `{"type": "pong", "event_id": <id>}` | Standard | Keepalive response to `ping` |
| `{"type": "client_tool_result", "tool_call_id": "<id>", "result": "<str>", "is_error": <bool>}` | Standard | Tool result submission |
| `{"type": "conversation_initiation_client_data", "conversation_config_override": {...}, ...}` | Standard | Session initialization |
| `{"type": "contextual_update", "text": "<str>"}` | Standard | Non-interrupting context update |
| `{"type": "user_message", "text": "<str>"}` | Standard | Text-mode user message |
| `{"type": "user_activity"}` | Standard | Keep-alive / prevent timeout |

**Critical implementation note for `user_audio_chunk`:**
The audio chunk message uses a **top-level key** (not a `type:` field):
```python
# From SDK source (verified):
json.dumps({"user_audio_chunk": base64.b64encode(audio).decode()})
```
This differs from OpenAI's `{"type": "input_audio_buffer.append", "audio": "<base64>"}` pattern. The planner must implement `append_client_audio()` with this exact format.

### Open Point 4: tool_result_submission_mode Value — RESOLVED

**Status:** RESOLVED (design assumption corrected)

**Finding:** ElevenLabs does NOT use the OpenAI `conversation.item.create` schema. It uses a **native `client_tool_result` message** sent directly over the WebSocket.

**Verified message format** (from SDK source):
```python
# github.com/elevenlabs/elevenlabs-python/src/elevenlabs/conversational_ai/conversation.py
response = {
    "type": "client_tool_result",
    "tool_call_id": parameters.get("tool_call_id"),  # NOT "call_id"
    "result": result or f"Client tool: {tool_name} called successfully.",
    "is_error": False,
}
```
[VERIFIED: github.com/elevenlabs/elevenlabs-python/src/elevenlabs/conversational_ai/conversation.py]

**Key difference from design assumption:**
- Design says `tool_result_submission_mode="conversation_item"` — this was WRONG
- Correct value: `"elevenlabs_native"` (custom string signaling the ElevenLabs wire format)
- Field name: `tool_call_id` (NOT `call_id`)

**Implication for `ELEVENLABS_REALTIME_CAPABILITIES`:**
```python
ELEVENLABS_REALTIME_CAPABILITIES = RealtimeProviderCapabilities(
    ...
    tool_result_submission_mode="elevenlabs_native",  # corrected from "conversation_item"
    ...
)
```

**`submit_tool_result()` implementation:**
```python
async def submit_tool_result(self, *, call_id: str, output: str) -> None:
    await self.send_json({
        "type": "client_tool_result",
        "tool_call_id": call_id,  # maps from contract's call_id to EL's tool_call_id
        "result": output,
        "is_error": False,
    })
```

**Note for planner:** If the consuming GlassAgents bridge checks `tool_result_submission_mode == "conversation_item"`, this change may require a bridge-side guard. Document in PITFALL section.

### Anti-Patterns to Avoid

- **`type` key in audio chunk:** Do NOT send `{"type": "user_audio_chunk", "audio": "..."}` — the correct format is `{"user_audio_chunk": "<base64>"}` with the key at top level.
- **`call_id` in tool result:** Do NOT send `{"call_id": ...}` — ElevenLabs requires `{"tool_call_id": ...}`.
- **`xi-api-key` in WebSocket URL:** The API key is only used in REST calls to get signed URLs for private agents, never in the WebSocket URL.
- **`conversation_item.create` for tool results:** The OpenAI pattern does not apply here; use `client_tool_result` message type.
- **`agent_response_complete` as primary RESPONSE_DONE signal:** This event was added in April 2026 API schema but not found in current SDK wire dispatch; do not rely on it as the sole trigger for `RESPONSE_DONE`.

## Common Pitfalls

### Pitfall 1: user_audio_chunk Message Format
**What goes wrong:** Developer mirrors the OpenAI audio format: `{"type": "input_audio_buffer.append", "audio": "..."}` — ElevenLabs silently ignores this and no audio is processed.
**Why it happens:** The OpenAI pattern uses a standard `type` discriminator. ElevenLabs uses a bare top-level key.
**How to avoid:** Use `{"user_audio_chunk": base64.b64encode(pcm16_audio).decode("ascii")}` — verified from SDK source.
**Warning signs:** Agent never responds to user speech; no error from server.

### Pitfall 2: tool_call_id vs call_id
**What goes wrong:** Tool result sent with `{"call_id": ...}` instead of `{"tool_call_id": ...}` — ElevenLabs server rejects or ignores it; tool call hangs.
**Why it happens:** The `RealtimeAdapterContract.submit_tool_result(call_id=...)` uses `call_id`. ElevenLabs wire format uses `tool_call_id`. The adapter must translate.
**How to avoid:** In `submit_tool_result()`, always map `call_id` → `"tool_call_id"` key.
**Warning signs:** Agent pauses indefinitely waiting for tool result.

### Pitfall 3: agent_response_complete as RESPONSE_DONE trigger
**What goes wrong:** Design relies on `agent_response_complete` to emit `RESPONSE_DONE`. This event is NOT in the current SDK wire dispatch; the connection loop never sees it and `RESPONSE_DONE` is never emitted.
**Why it happens:** The event was added to the API schema (April 2026) but has not appeared in the core SDK message dispatch as of v2.49.1.
**How to avoid:** Keep `agent_response_complete` in the dispatch table as a forward-compatible route to `RESPONSE_DONE`, but also verify whether the `audio` event sequence has a natural end-of-turn signal. If not, map the absence of `RESPONSE_DONE` explicitly.
**Warning signs:** Consumer never receives `RESPONSE_DONE`; event loop runs indefinitely after agent speaks.

### Pitfall 4: xi-api-key in WebSocket URL
**What goes wrong:** Developer adds `xi-api-key` as a query parameter to the WebSocket URL for private agents, exposing the key in logs.
**Why it happens:** Misunderstanding that the key must be on the connection itself.
**How to avoid:** For private agents, the correct flow is: REST call (with `xi-api-key` header) → get `signed_url` → connect WebSocket to `signed_url` (no header). The adapter's `base_url` only holds the base WSS endpoint; the key is used in the REST flow, not the WebSocket URL.
**Warning signs:** `_safe_url()` unit test fails; key appears in log output.

### Pitfall 5: No agent_response_complete → RESPONSE_DONE mapping ambiguity
**What goes wrong:** Without a clear RESPONSE_DONE signal, GlassAgents bridge may send tool results or follow-up audio too early.
**Why it happens:** ElevenLabs handles turn-taking server-side; unlike OpenAI's `response.done`, there is no single clean RESPONSE_DONE analog in the current wire protocol.
**How to avoid:** Watch for `agent_response` (text complete) or absence of further `audio` events. The planner should add a PITFALL comment in the code noting this gap.
**Warning signs:** Consumer receives `RESPONSE_DONE` too early or never.

### Pitfall 6: session_sample_rate = 16_000 (different from other providers)
**What goes wrong:** Consumer sends 24 kHz audio (the `INPUT_AUDIO_SAMPLE_RATE` default from `contracts.py`) — ElevenLabs expects 16 kHz and audio quality degrades or is rejected.
**Why it happens:** All other providers use 24 kHz; ElevenLabs is the exception (per PROV-FUT-03 prep in `contracts.py`).
**How to avoid:** `ElevenLabsRealtimeConfig.session_sample_rate = 16_000` communicates this. Consumer must re-sample if needed. The capability field `session_sample_rate=16_000` in `ELEVENLABS_REALTIME_CAPABILITIES` advertises this.
**Warning signs:** Audio sounds chipmunk-like or distorted; ElevenLabs transcripts incorrect.

### Pitfall 7: EU API Key is a Separate Key
**What goes wrong:** Consumer uses their global `xi-api-key` with the EU endpoint `wss://api.eu.residency.elevenlabs.io` — gets 403 Forbidden.
**Why it happens:** EU environment has its own separate API keys provisioned by ElevenLabs Enterprise support.
**How to avoid:** Document in GDPR guide: EU data residency requires (a) Enterprise plan, (b) a SEPARATE EU API key (not the global key), (c) EU agents must be created in the EU environment.
**Warning signs:** HTTP 403 on the signed-URL REST call or WebSocket connect.

### Client skeleton (auth + URL pattern)

```python
# Source: Derived from openai.py structure + SDK source auth flow (2026-05-25)
class ElevenLabsRealtimeClient(BaseRealtimeWebsocketClient, RealtimeProvider):
    def __init__(self, config: ElevenLabsRealtimeConfig, *, trace_events: bool = False) -> None:
        if not config.api_key.strip():
            raise ValueError("ElevenLabsRealtimeConfig.api_key must be non-empty.")
        if not config.agent_id.strip():
            raise ValueError("ElevenLabsRealtimeConfig.agent_id must be non-empty.")

        url = f"{config.base_url}/v1/convai/conversation?agent_id={config.agent_id}"
        # xi-api-key: NOT in WebSocket URL — used in REST call to get signed URL for private agents
        # For public agents: no auth header needed on WebSocket connection
        super().__init__(url=url, headers={})

        self._config = config
        self._trace_events = trace_events

    def _connection_error_endpoint(self) -> str:
        # agent_id is not a secret; base_url has no key embedded
        return f"{self._config.base_url}/v1/convai/conversation?agent_id={self._config.agent_id}"
```

## Security Domain

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | yes | `xi-api-key` header for REST only; signed URL for WebSocket; never in WS URL |
| V3 Session Management | yes | Each WebSocket connection is one session; clean close on error |
| V4 Access Control | no | Agent access control is in ElevenLabs dashboard, not in adapter |
| V5 Input Validation | yes | Fail-fast on empty `api_key` / `agent_id` before network I/O |
| V6 Cryptography | no | No custom crypto; TLS handled by `websockets` library |

### Known Threat Patterns

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| `xi-api-key` in logs / error messages | Information Disclosure | `_connection_error_endpoint()` never embeds key; key only used in REST call |
| EU key used with global endpoint | Elevation of Privilege | Document: EU key only works with EU endpoint |
| Signed URL reuse after 15-min expiry | Spoofing | Document: signed URL is single-use within 15-min window; for adapter, pre-fetch before `connect()` |
